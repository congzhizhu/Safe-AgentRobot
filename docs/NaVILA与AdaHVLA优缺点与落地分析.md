# NaVILA 与 AdaHVLA 优缺点及融入本项目可行性分析

> 基于两篇论文（arXiv 2412.04453 / 2609.29204）与对应开源仓库一手资料整理。
> 结论性判断（尤其「融入本项目能实现什么」）为结合 Safety_Agent 项目现状的分析，需结合实际验证。

---

## 一、两个项目的优缺点

### 1. NaVILA（RSS 2025，两级框架）

**优点**

- **两级解耦、跨机器人泛化强**：上层 VLA 只输出「前进 75cm」这类带空间语义的中层语言动作，下层 locomotion 策略落地执行。同一 VLA 不重训即可迁移到 Go2、H1 人形、Booster T1。
- **天然带避障**：下层是 LiDAR 高度图驱动的 RL 策略，能避让障碍物（含透明玻璃、强光），即使上层 VLA 未看到障碍也能躲。
- **数据来源广**：首创「直接在人类 YouTube 第一视角视频上训练」改善连续环境导航，叠加 VQA 数据增强推理能力。
- **性能实证充分**：R2R-CE SR 54.0（超此前 SOTA NaVid 17 点）、真机 Go2 25 条指令 88% 成功率。
- **代码/权重/数据全开源**：训练代码、预训练权重（navila-siglip-llama3-8b-v1.5-pretrain、navila-llama3-8b-8f）、数据集标注均放出。

**缺点**

- **训练成本极高**：VILA 8B 大模型 + 多模态导航数据 + 仿真，视觉指令调优需 4 节点（32×A100）18 小时。
- **环境安装极重且脆弱**：评估依赖 Habitat-Sim/Lab v0.1.7 旧版源码编译 + FlashAttention2 + 改 transformers/deepspeed 源码 + NumPy 兼容补丁，极易装挂。
- **推理慢、显存大**：单张 RTX 4090 约 1 FPS，需外部 GPU，机载部署是未来方向。
- **纠错能力弱**：论文明确记录「正确遵循指令但偏离后无法有效纠错」，正是需 AdaHVLA 补的地方。
- **sim2real 有落差**：不用 Oracle 低层策略时 Go2 成功率掉 15%、H1 掉 27%。

### 2. AdaHVLA（arXiv 2609.29204）

**优点**

- **不改 VLA 参数、只改协调代码**：把「任务级推理 + 记忆」与「VLA 局部执行」粘合，轻量、可解释、可编辑。
- **方法论严谨**：可测试协调假设（四要素）+ 归因门 χ（只把「机制真触发且未提前发散」的改进记到假设头上）+ 修订图（保留候选与证据），避免无效重复尝试。
- **提升巨大**：导航 2.5%→57.5%，操作最高 +30.8 点。
- **消融揭示关键机制**：完成检查（57.5%→29.2%）、恢复（L2 38.3%→23.3%）是最有价值的两个能力。
- **代码开源、有样例 harness**：提供 Go2 仿真导航完整示例，harness.py / adaptation.py 等可直接改。

**缺点**

- **真实世界部署部分未发布**：README 明确标注 "The real-world deployment part is coming soon"。
- **依赖极重**：Isaac Sim 4.1.0 + 两套 Python 环境 + NVIDIA GPU + 一个「支持图像输入、JSON 输出的视觉推理 API」（需外部 LLM）。
- **强绑定 NaVILA**：示例 harness 执行器就是 NaVILA，要跑通完整链路得先装好 NaVILA，成本叠加。
- **适应增益依赖底层 LLM 能力**：6 种适应模型差距达 25.8 点。
- **基础模型系统性错误无法消除**：解耦上下文治不了共享基础模型的视觉/空间推理错误。
- **任务越复杂越难统一预设**：各协调机制价值随任务复杂度变化。

## 二、融入本项目能实现什么

> 前提：本项目执行层是「SDK2 DDS 直控 + 云端多模态诊断」，与 NaVILA 的 VLA、AdaHVLA 的 NaVILA 执行器都不是一回事。直接跑它们的代码不可行，可落地的是「吸收机制思想」到 `patrol.py` 编排层。

### 短期（不换执行层，改 `patrol.py` 编排逻辑即可）

1. **补「失败恢复」机制**（抄 AdaHVLA Recovery，最值钱）
   - 现状：狗站不起来、移动失败就 `return` 直接终止。
   - 可实现：给 `execute_plan_iter` 加「动作超时检测 → 重试 N 次 → 仍失败才降级/终止」，并记录失败原因进报告。

2. **补「完成检查」**（抄 AdaHVLA Completion，消融最关键）
   - 现状：走完脚本就算完成，未验证是否真到目标点、真拍到照片。
   - 可实现：每个动作后校验「狗是否还站着、相机是否返回有效图像、移动是否到位」，未达标触发重试或纠正。

3. **补「进度追踪」**（抄 AdaHVLA Progress）
   - 现状：`ZONES` 路线写死，`TURN_DEG_PER_SEC` 靠人工标定。
   - 可实现：记录每步实际状态/耗时/位置估算，反馈到后续动作，让「转多少度、走多久」自适应。

### 中期（把「写死的策略」变成「可修订的配置/代码」）

4. **把 `ZONES` 路线 + 诊断提问 `question` 变成可自动优化的配置**（抄 harness 可编辑思想）
   - 现状：路线和提问硬编码，环境/隐患类型一变就得手动改。
   - 可实现：让狗跑几次后，用执行证据自动修订「每段走多久、转几度、拍几张、诊断怎么问」。

5. **引入「归因门」避免误判**（抄 Attribution Gate）
   - 现状：没有「这次改动到底有没有用」的判断标准。
   - 可实现：改完路线/提问后，只在「机制真触发且未提前跑偏」时才把改进归功于这次改动，避免靠单次偶然成功下结论。

### 长期（补底层能力，重且难）

6. **底层避障**（抄 NaVILA 下层 RL 策略）
   - 现状：「速度×时间」开环走位，无避障，会撞东西。
   - 可实现：引入 LiDAR 高度图 + 视觉运动 RL 策略，让狗走位时自主避障——解决「撞东西」的根子，但训练成本高、需 GPU。

7. **自然语言直接指挥走位**（抄 NaVILA 中层动作语言）
   - 现状：走位靠预设路线或简单速度指令。
   - 可实现：让模型把「往前走 1 米再右转」直接翻译成带空间语义的动作，替代硬编码。

---

## 三、结论

- **协调层**（抄 AdaHVLA）：轻量可行，短期可落地——优先做「进度追踪 + 失败恢复 + 完成检查」。
- **执行层避障**（抄 NaVILA）：重且难，长期方向。
- 建议优先把 AdaHVLA 的三项机制落地到现有 `patrol.py`，保留 DDS 直控不变，再逐步引入可修订的路线/提问配置。
